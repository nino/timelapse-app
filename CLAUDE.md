# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this app is

A Tauri 2 desktop app (macOS-focused) that runs a background "photographer" loop capturing one screenshot per second of the focused screen, stores them as PNGs under `~/Timelapse/YYYY-MM-DD/00001.png`, and serves a React frontend for scrubbing through any day, whether that day survives as screenshots or only as a rendered `.mov` timelapse. The photographer starts automatically on app launch (see `src-tauri/src/lib.rs::run`).

## Commands

**The package manager is [Bun](https://bun.sh)** — `bun install`, `bun.lock`. Don't use yarn or npm; there is no `yarn.lock` and `package-lock.json` should never be committed.

Frontend / build:
- `bun run dev` — Vite dev server on port 1420 (Tauri's `beforeDevCommand`)
- `bun run build` — `tsc && vite build` (produces `dist/` consumed by Tauri)
- `bun run tauri dev` / `bun run tauri build` — run/bundle the desktop app
- `bun run lint` / `bun run lint:fix` — oxlint over `.ts`/`.tsx` (Rust dir is ignored)
- `bun run version:bump major|minor` — raises the version floor in **both** `package.json` and `src-tauri/tauri.conf.json` in lockstep (see Releases); always use this rather than editing versions by hand, and never bump the patch in a PR. Bun runs the TypeScript file directly, so there is no `tsx`/`ts-node` step.

Tests:
- `bun test` (also `bun run test`) / `bun run test:watch` / `bun run test:coverage` — Bun's own test runner, with happy-dom registered as the DOM; Tauri APIs are mocked in tests. Filter with `bun test <path>` or `bun test -t <name>`
- `cd src-tauri && cargo test` — Rust unit + Tauri command tests (uses `tempfile` for filesystem isolation). Runs in cloud sessions: the SessionStart hook installs Tauri's Linux libraries and ffmpeg. On a Mac, run `bun run fetch:ffmpeg` once first, because the build needs the bundled ffmpeg (see below)
- Single Rust test: `cargo test <test_name>` from `src-tauri/`

CI: `.github/workflows/ci.yml` runs on every PR and push to `main`. A Linux job runs lint, `bun run build` (tsc + Vite) and `bun test`; a macOS job fetches the bundled ffmpeg, puts it on `PATH` for the tests, and runs `cargo test --workspace` (the app and `frame_source`). The Rust job builds the frontend first, because `generate_context!` needs `dist/` to exist.

Note: Vite and oxlint run under **Node**; the frontend tests run under the **Bun** runtime via `bun test`. There is no Vitest.

**Frontend test setup.** `bunfig.toml` preloads `src/test/happydom.ts` (registers happy-dom globals; must load first) and then `src/test/setup.ts` (jest-dom matchers, Tauri mocks, `URL.createObjectURL` stubs, `cleanup`). Import test APIs from `bun:test`. Two Bun-specific rules:
- **`mock.module` is process-wide.** Bun runs every test file in one process, so a module mocked in one file is mocked for all of them. The Tauri modules (`@tauri-apps/plugin-fs`, `@tauri-apps/api/core`) are therefore mocked once, in `setup.ts`, with every export any test needs — add new exports there rather than calling `mock.module` in a test file. To fake one of the app's own modules, use `spyOn(namespace, 'fn')` and `mockRestore()` it in `afterAll`, as `App.test.tsx` does for the library hooks; a `mock.module` there would replace the real hooks under `useLibrary.test.ts`.
- **No `vi.mocked`.** Use `mocked(fn)` from `src/test/mocked.ts`, a type-only cast to Bun's `Mock<T>`.

## Architecture

**Two-process split.** All filesystem and capture work lives in Rust (`src-tauri/src/`); the React frontend gets everything from Rust (the `list_days`/`get_day`/`get_frame_time` commands and the `frames:` URI scheme) and uses `@tauri-apps/plugin-fs` (scoped in `src-tauri/capabilities/default.json`) only to watch the library for changes.

**Rust side — `src-tauri/src/`:**
- `lib.rs` — defines `#[tauri::command]`s and holds the `PhotographerState = Arc<Mutex<Option<Photographer>>>`. Each state-backed command is a thin shim over a `*_impl(&PhotographerState, …)` function; `tauri::State` wraps a private reference with no public constructor, so that split is what makes the logic unit-testable. The Photographer is auto-started in `setup()` after a 1s delay; `evict_old_cache()` runs first to drop cache folders older than 15 days.
- `timelapse.rs` — the `Photographer` runs a tokio loop: capture focused screen (on macOS straight from Core Graphics as raw BGRA pixels, skipping the `screenshots` crate's full-size PNG encode that would only be decoded again; elsewhere its PNG, decoded) → Box-filter it into a black-letterboxed 1800×1124 frame (`fast_image_resize`, pure Rust, cropping off Core Graphics' row padding). A big screen that would get under 1 stored pixel per point in that frame (a 2560×1440-point monitor gets 0.7) is stored in its own shape, without bars, at 1.4 px per point or the capture's own density if lower (`frame_size`: 3584×2016 at 2x, 2560×1440 at 1x), because OCR loses most small text below that; the converter still letterboxes every frame into its 1800×1124 video, so only the PNGs grow, and the viewer sizes frames by their own dimensions → drop if all-black, before writing anything → name as `NNNNN.png` (next-after-max in the day dir) → write a row to SQLite. Black images get a 10s backoff; a failed capture is retried on the next second, and only from the third failure in a row (`FAILURES_BEFORE_BACKOFF`, reset by any capture that works) does it wait 60s. The active window only picks which screen to capture (the one holding it, not the one under the mouse pointer, so that Cmd-Tabbing to a window on another screen is followed without moving the pointer); when there is none (one of the app's own modal dialogs is open, or the focused window just closed) it captures the screen it used last, so a dialog never stops capture. Errors are appended to a bounded in-memory log (max 10 000 entries).
- `database.rs` — `ScreenshotDatabase` wraps a `rusqlite` connection at `~/Timelapse/screenshots.db`. Has its own `migrations` table, and every migration runs inside the one `IMMEDIATE` transaction in `run_migrations`: check applied → run → record. `split_timestamps` splits the legacy `creation_date` column into `created_at` (UTC) and `local_time` (Local). `add_day_and_ocr` adds `screenshots.day` (the day folder name, back-filled from `local_time`) and the OCR tables: `ocr_frames` (text, one line per box, and the boxes packed as 8 bytes a line by `pack_boxes`; one row per frame whose text differs from the day's previous row), its FTS5 index `ocr_fts` (kept in sync by triggers), and `ocr_progress` (per day, the highest frame OCR has handled, with every frame below it handled too). `ocr_video_positions` adds `ocr_progress.by_position`: for a day read from video, `frame_number` and `last_frame` are 1-based positions in the day's videos (frame-source index + 1), not `NNNNN`, and `ocr_done_through` ignores such rows so the converter never mistakes one for the other. `compact_ocr_frames` replaced the old `lines_json` column (which repeated every line's text, with full-precision floats) by `boxes`, dropped rows repeating the previous row's text, and vacuums once. `add_video_frames` adds `video_frames`: for each hourly video, which screenshot (day, frame number) each of its frames came from and that screenshot's capture time.
- `ocr.rs` — background OCR, started in `setup()` after the Photographer on a background-priority thread with its own DB connection. Walks day folders in frame order, reads a frame with Apple Vision (accurate mode; macOS only, via `objc2-vision`) (a frame bigger than 1800×1124 in overlapping tiles of about 1200×750 pixels, one request per tile limited by its region of interest; `ocr_tiles::assemble` trims lines cut by a tile edge to their own words, joins them, and keeps a line two tiles saw whole once: Vision judges text size against the whole image, so a big screen read whole lost three quarters of its words) only when its quarter-size thumbnail differs from the last frame read, and moves `ocr_progress` forward for read and skipped frames alike. A recognizer failure is not taken for a bad frame: the pass stops without moving the mark and tries that frame again a minute later (`State::Retrying`), passing over it only on the third failure; an unreadable image is passed over at once. Vision can lose the Neural Engine for the rest of a long-running process's life (every request then fails with `CRImageReaderError error 1` after an E5RT error in the system log, while a new process reads the same frame fine); `usesCPUOnly` and `setComputeDevice` don't keep it off the Neural Engine, so only a relaunch recovers. Only on AC power, and never on a frame less than 10 s old (it may still be written, or about to be deleted as all-black). `ocr_covers` is the check the video converter makes before deleting an hour's PNGs. When a pass finds no new screenshots, it reads up to 1800 frames of days that only exist as video (the old script's `.mov`s, or hours converted before OCR existed), newest day first: `FrameSource::video_only_day` lists the videos and `stream_video` pipes decoded frames from ffmpeg as PPM, so nothing is cached on disk except the one changed frame being read. Days OCR started from screenshots are left to the screenshot pass. Tests use a fake `TextRecognizer`; the real one has an `#[ignore]`d test driven by `OCR_TEST_IMAGE`.
- `frame-source/` — **a separate crate** (workspace member, no Tauri dependency) that answers "frame N of day D" and hides where frames come from. A day is assembled hour by hour, in clock order: an hour that still has screenshots is served from them; an hour whose screenshots the converter deleted is served from its `YYYY-MM-DD--HH-MM-SS--hourly[-N].mov` (parts in order). Screenshots win when both exist. Only a day with neither falls back to the old script's whole-day videos (`YYYY-MM-DD--HH-MM-SS.mov|mp4`, root or day folder), played back to back in start order; byte-identical duplicates and files ffmpeg can't read are skipped. It runs only `ffmpeg` (never `ffprobe`, which the app doesn't bundle): the app hands it `Tools::new(paths::ffmpeg())`, the bundled sidecar, and the crate never looks for ffmpeg itself. Frame counts come from a packet-only `-c copy -f framecrc` pass. The hour of a screenshot is the local hour of its mtime, clamped to its day folder's date (a frame taken at 23:59:59 can be written after midnight), the same bucketing `converter.rs` uses: both call `frame_source::filed_at`. Video frames are decoded by ffmpeg in chunks of `CHUNK_FRAMES` (150) into a size-capped LRU cache under the OS cache dir (`<app cache>/<Timelapse|Timelapse_dev>/frames/`, 2 GiB). Read-ahead (`FrameSource::read_ahead`, switched on by the app) decodes the next chunk before the viewer gets there: once a requested frame is within `READ_AHEAD_FRAMES` (100, the Alt+arrow step) of an undecoded chunk in the direction the viewer is moving (both ways for the first request), a single background thread decodes it with ffmpeg at nice 10, nearest first; each new request replaces its queue. After each chunk it calls back with the day, which `lib.rs` emits as `frames-decoded` so `usePendingFrames` re-asks `get_pending_frames`. Timestamps come from the DB keyed by **(day, frame number)**, then file mtime. Hourly-video frames take the time the converter recorded in `video_frames` (`exact: true`), when the record has exactly as many rows as the video has frames. A video converted before that was recorded lines its frames up with the hour's DB rows in frame-number order, starting at the first row not before the name's time (`exact: false`); with no rows, the name (the first frame's time) plus one second per frame. A legacy video's name is *not* a start time (the old script named videos after the capture day and the time it ran), so legacy days take the day's DB rows in frame-number order, but only when their count equals the day's frame count (checked on the real library: it does, from 2025-11-11 on); otherwise no time. Test it with `cargo test -p frame_source` — it needs only ffmpeg, so it runs where the app crate can't build.
- `activity.rs` — the in-memory report behind the Activity window (Window → Activity, macOS menu built in `lib.rs::app_menu`). The Photographer, `Converter` and `OcrWorker` each take an `Arc<Activity>` through `reporting_to` and update it as they go (captures, encode started/finished and its progress, read from ffmpeg's `-progress pipe:1` `frame=` lines, backlog counted, OCR pass size and each frame handled, and when each loop sleeps until). `get_activity` returns a `Snapshot` of it plus the power source (`pmset`, reused for 10 s), so polling it never scans the library or the DB.
- `boost.rs` — a boost (Activity window: a length, "Boost!", "Also on battery"; `start_boost`/`stop_boost`/`set_boost_allow_battery`) lets conversion and OCR stop saving CPU until it ends or is stopped; it is in memory only, so quitting ends it. While it is on, a running ffmpeg is taken out of `taskpolicy -b`'s background policy (`setpriority(PRIO_DARWIN_PROCESS)`, put back when the boost ends), the OCR thread runs at the user-initiated QoS class instead of background, batches follow each other with no 10-minute gap, and, if it allows battery, both run unplugged (`Boost::may_work` replaces the bare `on_ac_power` checks). Starting or stopping one wakes sleeping workers (`Boost::sleep` for OCR, `boost::wait` for the converter), and during a boost that does not allow battery they re-check the power every 10 s (`BOOSTED_POWER_POLL`) instead of every 1 or 5 minutes; an expired boost takes effect at the workers' next check. `get_activity` reports it as `boost`. The same `Boost` also holds low-power mode (`start_low_power`/`stop_low_power`, the "Low power" button in the Activity window's Speed section), its opposite: for a while `may_work` is false even on AC power, so conversion and OCR sleep in `State::LowPower` until it ends and a running encode is paused as on battery; starting a boost or low-power mode replaces the other, and `get_activity` reports it as `lowPowerUntil`.
- `diagnostics.rs` — a log for Nino to upload when something looks wrong (there are no analytics): `<library>/diagnostics.db`, one `events` table (`at` local RFC 3339, `level`, `source`, `message`, `duration_ms`, JSON `data`). `diagnostics::info|warn|error(source, msg).took(d).data(json!(…)).record()` only sends down a channel; a `diagnostics` thread writes what has queued in one transaction (rollback journal, not WAL, so the file alone is the whole log). Before `diagnostics::init` (and so in every test) events go nowhere. Rows over 30 days old or beyond the newest 100 000 are pruned, and more than 600 events an hour are dropped and counted. Log changes, errors and finished work, never one row per frame: per-frame things go into a `Tally`, written as one `Summary` event an hour (capture timings and counts; OCR passes that keep up with new frames). `Activity` logs encodes, black-screen stretches and loops going to sleep for a different reason; `converter::on_ac_power` logs power-source changes; the boost commands, the updater, panics and uncaught frontend errors (`log_frontend_error`, `src/diagnostics.ts`) log too.
- `lib.rs` exposes it through the `list_days`, `get_day`, `get_frame_time` and `get_pending_frames` commands (the last lists the video stretches of a day not yet in the chunk cache, which the scrubber draws paler) and a `frames://localhost/<YYYY-MM-DD>/<index>` URI scheme (`http://frames.localhost/…` on Windows) that the `<img>` loads directly.
- `converter.rs` — the background video converter, started in `setup()` next to the Photographer. It replaces the old `all-timelapses-to-video` script: every PNG is bucketed by the local hour of its mtime, clamped to its day folder's date, and once an hour has ended (plus a minute's grace for late writes) it is encoded (the same ffmpeg/libx265 settings the script used) into `<root>/YYYY-MM-DD--HH-MM-SS--hourly.mov` (the time is the first frame's, clamped the same way; the `--hourly` tag is what distinguishes these from the old script's videos, whose time is when the script ran), and an hour whose `.mov` exists counts as done. Just before the video is renamed into place, `record_frames` writes its `video_frames` rows (a failure there is logged, not fatal); a video without rows gets them when its PNGs are about to be deleted, and an hour whose rows can't be written, or whose PNGs are no longer exactly the recorded ones (`matches_record`: a frame written after its hour was converted), keeps its PNGs. An hour is encoded only once OCR has handled all of its PNGs (`OcrCheck`; `setup()` passes `ocr::ocr_check`, over `ocr_progress`), and its PNGs are deleted only when that check still passes. One batch at a time, each starting 10 minutes after the previous one started while more OCR'd hours are waiting (an encode longer than that is followed straight away), only on AC power (`pmset -g ps` on macOS; any failure reads as battery), ffmpeg under `taskpolicy -b` on macOS, and a running encode is paused while the power is unplugged (ffmpeg is frozen with `SIGSTOP` and thawed with `SIGCONT` once it is back on AC power; `taskpolicy` execs ffmpeg in its own process, so the signal reaches it) and killed when the app quits or restarts (`kill_running_encode`, called on `RunEvent::Exit` and before the updater's `app.restart()`, which on the main thread skips `Exit`); ffmpeg is a separate process and would otherwise outlive the app. An interrupted hour is encoded again from its first frame on the next launch. Frames are hard-linked into `.cache/.convert-<video>/` as a gapless `%05d` sequence first, because ffmpeg's `%05d` input stops at the first numbering gap.

**Frontend — `src/`:**
- `App.tsx` is the entire UI: one view, a day picker (newest first, today auto-selected) and a scrubber. There are no Images/Videos tabs; whether a day is screenshots or video is the frame source's business. The `<img>` points at `frameUrl(day, index)` from `src/frames.ts`, gated by `useGatedImage` so only one frame loads at a time and each finished load jumps to wherever the scrubber is now (otherwise dragging across a video day queues a decode per chunk).
- **Styling follows Nino's Ninoes design system** (`nino/ninoes`, `app/app.css` and `app/components/ui/styles.ts`), copied in: the tokens (`bg-page`, `bg-card`, `text-fg`, `text-muted-fg`, `border-border`, `bg-primary`, …) are in `@theme` in `src/App.css` and redefined for dark mode there, so use them instead of raw colours. The colour values are no longer Ninoes' baby blue: Nino chose a higher-contrast "Ultramarine" palette (near-neutral greys, a saturated ultramarine accent, a canvas a clear step darker than the header and scrubber bars, solid borders), and the scrubber thumb is a 6px cyan playhead bar (`--color-playhead`) over an inset track (`scrub-track`, a gradient and a hairline ring); shared class strings are in `src/ui.ts`. Nino wants performance first: nothing uses a blurred shadow or the squircle `corner-shape` (WebKit repaints a blurred shadow on the CPU on every frame of a window resize, which made resizing sluggish; Chromium paints squircles three times slower). Prefer dropping an effect to keeping one that costs resize or scrub smoothness. The fonts (Bricolage Grotesque, Bevan) are bundled with `@fontsource`, not loaded from the network. The day picker (`src/DayPicker.tsx`) is the Ninoes Select, the Headless UI `Listbox` from Ninoes' `Pager.tsx`; tests open it by clicking the `Day` button and then the option.
- **Activity window.** `show_activity_window` opens a second window labelled `activity` on the same `index.html`; `main.tsx` renders `ActivityView` instead of `App` for that label. It polls `get_activity` once a second while visible (`hooks/useActivity.ts`) and counts down to each loop's `nextCheckAt` itself. Each "Last error" line has a Dismiss button (`dismiss_error`), which clears that error in the in-memory report only if it is still the one shown, so a newer error stays; errors live only in memory, so a relaunch starts clean anyway. Its capability is `capabilities/activity.json` (`core:default` only; no fs access).
- `hooks/useLibrary.ts` — `useDays()` (via `list_days`) and `useDay(date)` (via `get_day`: frame count and source). `useDay` returns `null` while a newly selected day loads, never the previous day's answer.
- **The data is live; there is no refresh button.** Both hooks re-ask Rust when `useDirectoryChanges` (`hooks/useDirectoryChanges.ts`) reports a change in the library root or the day folder. It uses the fs plugin's debounced `watch` (Cargo feature `watch`, permissions `fs:allow-watch`/`fs:allow-unwatch`) and falls back to polling every 3s if the watcher can't be created. `useLatestLoad` makes sure only the latest request per hook may publish, and reloads that find nothing new keep the old value so effects don't re-run every second.
- **The viewer follows the live edge.** The position is `{ day, index }` with `index: null` meaning "newest frame", so new captures are followed for free and scrubbing back stops following; a position recorded for another day counts as null, so opening a day lands on its last frame without first requesting frame 0. At midnight the selection moves to the new day only for someone following the previous newest day's live edge.
- The frontend talks to Rust via `invoke<T>(...)` for `list_days`, `get_day` and `get_frame_time` (wrapped in `src/frames.ts`), plus the start/stop/error-log commands, `search_ocr_day`/`get_match_lines`/`count_ocr_matches`/`get_ocr_version` (wrapped in `src/search.ts`, used by the find bar) and `search_ocr` (all days at once; not wired into the UI but tested). `get_screenshot_metadata` is no longer used by the UI: it looks frames up by number alone, which collides across days.
- **Find bar** (header): searches the selected day's OCR text as you type (`hooks/useOcrSearch.ts`). Matches are marked above the scrubber, back-to-back matches merge into one stop (`toStops`), Enter/Shift+Enter step through them, and the matching lines of the frame on screen are outlined once it has loaded (`get_match_lines`, which matches lines with the same FTS5 tokenizer as the index). "Also on" lists other days with matches; picking one opens it on its first match. Searches re-run only when `get_ocr_version` changes (it is checked on every library-root change; captures don't change it), and every search command opens the DB read-only (`ScreenshotDatabase::open_read_only`) so it never takes the write lock. A match is an OCR row keyed by `(day, frame_number)`; `search_ocr_day` turns it into a scrubber index with `FrameSource::indices_of_frames`: exact for screenshots on disk and for hourly videos with a matching `video_frames` record, an estimate for videos converted before that record existed (rank among the hour's DB rows), and on legacy-video days the rank among the day's DB rows when the counts agree (the `frame_time` rule).
- Keyboard: ArrowLeft/Right scrub by 1; Shift = 10; Alt/Option = 100, including when the slider has focus (the handler prevents its native step). Cmd/Ctrl+ArrowLeft/Right open the previous/next day. Arrows in the day picker and the find bar are left alone, Cmd/Ctrl ones included. Cmd/Ctrl+F focuses the find bar.

**Dev and release use different libraries.** Debug builds (`bun run tauri dev`) read and write `~/Timelapse_dev`; release builds (`bun run tauri build`) use `~/Timelapse`. **Rust owns this decision** — `TIMELAPSE_DIR_NAME` in `src-tauri/src/paths.rs`, switched on `cfg!(debug_assertions)` — and the frontend asks for it via the `get_timelapse_root_name` command, resolved in `main.tsx` before the first render. Build paths with `timelapseRoot()` from `src/timelapseRoot.ts`; never hardcode either name, and never re-derive the root from `import.meta.env.DEV`: `import.meta.env.DEV` and `cfg!(debug_assertions)` are different axes that disagree under `tauri dev --release` and `tauri build --debug`, which points the capture loop at one library and the viewer at the other. `capabilities/default.json` allow-lists **both** trees, because the `fs:scope` list is baked in at build time and cannot branch on the profile — so the isolation is enforced by the root the app asks for, not by the sandbox.

Two consequences worth remembering: `cargo test --release` compiles with `debug_assertions` off, so `TIMELAPSE_DIR_NAME` is the *production* name during release tests — every test must go through `Photographer::new_in` with a `TempDir` rather than `Photographer::new()`. And `setup()` creates the library directory eagerly, before the 1s delay that builds the Photographer, because the frontend's first `readDir` would otherwise fail on a fresh library.

**ffmpeg is bundled; nothing comes from Homebrew.** On macOS, `tauri.macos.conf.json` lists `binaries/ffmpeg` as an `externalBin` sidecar, which Tauri installs next to the executable (`Contents/MacOS/ffmpeg`) and signs with the app. `scripts/fetch-ffmpeg.ts` (`bun run fetch:ffmpeg`) downloads a pinned, checksummed static build with libx265 into `src-tauri/binaries/ffmpeg-<triple>` (gitignored; for `universal-apple-darwin` it fetches both architectures and `lipo`s them together); it runs in `beforeDevCommand`/`beforeBuildCommand`, and `build.rs` stops a macOS build that lacks it with a message saying to run it. Every ffmpeg call goes through `paths::ffmpeg()`, which prefers that sidecar and falls back to `ffmpeg` on `PATH` (tests, Linux). To upgrade ffmpeg, change the pin's URL and sha256 together. The config is macOS-only so a Linux `cargo test` never needs the binary.

**Tauri ↔ frontend trust boundary.** The `fs` plugin's scope (`capabilities/default.json`) permits `$HOME/Timelapse` and `$HOME/Timelapse_dev` up to two levels deep, and their `.cache/` up to three. If you add a new path the frontend needs to read, extend the `fs:scope` allow-list — otherwise `readFile`/`readDir` will fail at runtime, not at build time.


**Test isolation seams.** `Photographer::new()` resolves the profile's library root and delegates to `Photographer::new_in(root)`; tests always use `new_in` with a `TempDir` so `cargo test` never reads, writes, or captures into a real library, in either profile. `Photographer::start()` calls `tokio::spawn`, so anything touching it needs `#[tokio::test]`, and the test must call `stop()` before its first yield point — that is what makes the capture loop exit on its first poll. An `.await` between start and stop lets it capture the real screen.
## Releases

`.github/workflows/release.yml` builds, signs (Developer ID, hardened runtime), notarises and staples the app and a DMG on every push to `main`, and publishes them as their own GitHub release, tagged `v<version>` and marked latest, so every old version stays downloadable; pushing the `beta` tag publishes a prerelease instead. It follows nino/worktree-manager's release workflow and uses the same secret names.

**Version numbers.** From 0.2.0 on, stable versions are contiguous semver: each release to main gets the highest `v*` tag reachable from it plus one patch, or `tauri.conf.json`'s version when that is higher (which is how `bun run version:bump minor` starts `0.3.0`). The rule is `nextVersion` in `scripts/version.ts`; `bun scripts/release.ts version` prints it for HEAD and the workflow passes it to `tauri build` as a `--config` override. **PRs never change the version**: no PR touches a version number, so PRs merged in parallel can't conflict over it or claim the same one, and the number is decided only when the merge is released. The tag is created by `gh release create` when the release publishes, and nothing is committed back. Main's releases queue rather than cancel each other (a running one finishes; only the newest waiting push builds next), so a merge that lands while another is releasing shares the next version with whatever else is waiting. A re-run on a released commit rebuilds that same version. A beta is `<next stable version>-beta.<run number>`. The release notes are that version's change-log entries (`bun scripts/release.ts notes <version>`). Releases before 0.2.0 were numbered `<major>.<minor>.<commit count>` under one rolling `latest` release, which the first versioned release deletes.

**Auto-update.** `src-tauri/src/updater.rs` (release builds only; a debug build would replace itself with the release one) checks `releases/latest/download/latest.json` at launch and hourly through `tauri-plugin-updater`, installs a newer version, and relaunches once the window is not focused. It does so only while "Update automatically" is on in Settings, and only when this account can replace the bundle by itself (`can_install_silently`): in a folder it can't write to, such as /Applications for a non-admin user, the plugin asks for an admin password, which the background loop must never pop up unasked. When "Check for Updates…" installs into such a folder, `install_with_password` does the plugin's job itself: it downloads (which checks the signature), unpacks, and has `osascript` ask for the password and move the app into place in a separate process, because the plugin runs its AppleScript prompt on the main thread and every window beachballs until it is answered. The app menu's "Check for Updates…" checks whatever the setting says and reports in a `tauri-plugin-dialog` dialog; the two share `UpdaterState`, so they never install at once. The workflow writes that `latest.json` and uploads it with a minisign-signed `.app.tar.gz`; `createUpdaterArtifacts` is switched on only by the workflow's `--config` override so a local `tauri build` needs no updater key. The app trusts only `plugins.updater.pubkey` in `tauri.conf.json`, which must match the `TAURI_SIGNING_PRIVATE_KEY` secret: losing that private key means installed copies can never update again, and the workflow refuses to run while the pubkey is the placeholder.

**Remembered state.** `app_state.rs` keeps `state.json` in `<app config dir>/<Timelapse|Timelapse_dev>/` (per profile, since the viewer position names a day in one library): each window's outer top-left and inner size in logical pixels and whether it is open, plus the viewer's `{ day, index }` (`day: null` = follow the newest day's live edge, `index: null` = the day's newest frame). Changes are kept in memory and written by a background thread once they have stopped for a second; `before_quit` (on `RunEvent::Exit` and before the updater's `app.restart()`) writes it at once and kills the running encode. Window places come from `on_window_event` (`Moved`/`Resized`; minimised and full-screen windows are skipped); a window counts as closed only on `CloseRequested`, which ⌘Q never sends, so whatever is open at quit reopens. The main window has `create: false` in both `tauri.conf.json` files and is built in `setup()` by `open_main_window` after the Activity and Settings windows reopen unfocused, so it ends up in front and focused. `app_state::fit` moves a window whose title bar would be out of reach onto a screen's work area. Settings reopens at its saved position and height (only a starting guess: `grow_settings_window` still fits it to its content, keeping its top-left corner). The page saves the viewer position 500 ms after it last changed (`src/viewerPosition.ts`); `main.tsx` reads it before the first render and `App` opens that day, or the newest day when it is gone.

**About window.** The app menu's About item is the app's own (`show_about_window`, label `about`, capability `capabilities/about.json`), not the standard About panel, so it can show a change log: `src/AboutView.tsx` shows the name, `getVersion()` and the changes grouped by day. The change log is read from git at build time by `scripts/changelog.ts` (a Vite plugin in `vite.config.ts` serves it as `virtual:changelog`, typed in `src/vite-env.d.ts`): one entry per PR on main's first-parent line, titled with the PR's title and numbered with the version that first shipped it: the next `v*` tag at or after its commit, the version the next release will get (`nextVersion`) for commits not released yet, and `<major>.<minor>.<commit count>` for commits from before 0.2.0 (`versions` in `scripts/changelog.ts`). Commits pushed straight to main, dependency bumps, and PRs that only touched docs, CI or tests are left out. So PR titles are what users read: write them in plain language. Outside a git checkout the log is empty.

**Settings window.** App menu → Settings… (⌘,) opens a non-resizable window (`src/SettingsView.tsx`, label `settings`, capability `capabilities/settings.json`) built like the Activity window: `main.tsx` picks the view by window label. As on macOS there is no Save button: each change calls a command that saves it at once. `settings.rs` keeps `settings.json` in the app config dir (not the library, so dev and release builds share it), written atomically; a missing or unreadable file means defaults, and new fields need `#[serde(default)]` values. The one setting so far is `updateAutomatically` (default on); turning it on wakes the updater loop to check straight away.

The build is Apple Silicon only (the runner's architecture). The job runs `bun run fetch:ffmpeg` before `cargo test`, because build.rs needs the sidecar and only `tauri build` fetches it on its own.

## Things to know before changing behaviour

- **Filename format is load-bearing.** Screenshots are `NNNNN.png` (5-digit, zero-padded). `next_filename` scans the dir, parses every numeric stem, and returns `max + 1`. The frame source parses the same format (`parse_screenshot_name`) to order frames and look up timestamps. If you change one, change both.
- **All-black frames are never written.** `is_image_all_black` runs on every fitted frame before it is saved; a black frame is dropped (its number is reused by the next capture) and the loop sleeps 10s. Numbering still has gaps from older libraries, where black PNGs were written and then deleted, and from files removed by hand — `next_filename` and the converter handle them.
- **Frames are written atomically.** `store_frame` saves to `.NNNNN.png.tmp` beside the target and renames it into place, so a crash or full disk never leaves a truncated `NNNNN.png`. The temp name is a dotfile and not a `.png` (so `parse_screenshot_name` rejects it), which keeps it out of the frame source, the converter and `next_filename`.
- **Videos are a day source, not a separate list.** `library::parse_video_name` keys on the two name formats above; anything new that writes videos must use one of them and rename into place only when complete.
- **Decoded chunks stage, then publish.** ffmpeg writes a chunk into `.<chunk>.partial/` and it is renamed into place only on success, so a chunk folder that exists is whole. `ChunkCache::open` clears leftover partials. The old `extract_video_frames` command and its `~/Timelapse/.cache/<video>/` folders are gone; `evict_old_cache` still clears those out over 15 days.
- **Frame numbers are per day.** `NNNNN` restarts at 1 in every day folder, so anything that stores or looks up a frame keys it on `(day, frame_number)`, as `screenshots.day`, `ocr_frames` and `ocr_progress` do.
- **Screenshots are deleted only after video conversion and OCR.** Nino wants PNGs gone once their image information is kept as video and their text as OCR — never on video alone. `OcrCheck` is where OCR says an hour is done (`ocr::ocr_check`, over `ocr_progress`); the converter waits for it before encoding an hour and again before deleting its PNGs. The video's file name is the only "converted" marker, so deleting a `.mov` before its PNGs go makes that hour convert again. In today's folder the hour holding the highest-numbered frame is never deleted, because `next_filename` is `max + 1` and deleting the newest frame would restart today's numbering at `00001`.
- **The DB lives next to the screenshots.** `~/Timelapse/screenshots.db` (or `~/Timelapse_dev/screenshots.db` in a debug build). Don't move it without updating `Photographer::new_in` and the migration logic.
